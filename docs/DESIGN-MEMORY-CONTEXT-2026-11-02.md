# 上下文与记忆处理方案（2026-11-02）

> 背景：她丢上下文分两类——**该看的时候没看**（判定早于理解）和**看了也没存住**（存储有损）。
> 本文把两类拆成四层，给出每层的数据结构、触发条件、预算与验收，先设计后动手。

---

## 0. 现状测量（基线）

```
timeline 总 57 条：group 40 / QQ 私聊 12 / 网页 5
单条文本长度：p50=12 字，p90=277 字，max=500 字（写入时截断）
prompt 预算：群 3000 字 / 私聊 2500 字（按字数，不按 token）
旧存储：groupBuffer 30 条、prompt 取 20 行、history 16 条
```

p50 只有 12 字，说明大部分是短句/表情式回复；真正吃预算的是 p90 的长回复。
问题不在「总字数」，在**结构**和**选择**。

---

## 1. 判据（做到什么算好）

| 编号 | 场景 | 通过标准 |
|---|---|---|
| A1 | 指代 | 群里连发 3 张图后问「这个」→ 能说出是哪张（photo id / 发送者） |
| A2 | 复述 | 不调工具，原样复述上一条用户消息 |
| A3 | 30 分钟 | 静默 30 分钟后再问「刚才说到哪」→ 能给出话题与结论 |
| A4 | 隔天 | 第二天问「昨天聊了什么」→ 能列出 episode 标题，不编造 |
| A5 | 预算 | 任何一次 prompt 的原文段 ≤ 预算；被压缩/丢弃的内容有标记 |
| A6 | 可追溯 | 当前 episode 内的任意一条，要么在原文里，要么在摘要里，不能既不在也没标记 |

A1/A2 今天已能过（timeline 验证过复述）；A3/A4 是新增能力。

---

## 2. 四层模型

```
L0 消息成形   一条消息 = 文本 + 图 + 引用 + 连发合并 + 线程归属
L1 工作记忆   这一轮真正塞进 prompt 的内容（按预算选，不按条数切）
L1.5 压缩     超预算时，把最老的一段压成摘要，而不是丢掉
L2 段落结算   静默 20 分钟 → 一段对话结算成一个 episode
L3 长期记忆   episode / 决定 / 承诺 进记忆库；检索修成 pre-filter
```

---

## 3. L0：先成形，再判定

### 3.1 事件信封

```json
{
  "eventId": "msg-id",
  "at": "2026-11-02T12:00:00+08:00",
  "place": "group:1000000",
  "from": { "id": "qq-your-org", "name": "★大風起", "role": "owner|member|her" },
  "text": "分析下这张图",
  "images": [{ "photoId": "img-abc", "mime": "image/jpeg" }],
  "quote": { "messageId": "…", "text": "…", "images": ["img-xyz"] },
  "parts": [{ "at": "…", "text": "…" }],
  "threadId": "…"
}
```

### 3.2 规则

1. **先补全**：图、引用、连发（同一人 90 秒内）在**判定之前**完成。
   - 图：收到即下载 → `savePhoto` → 拿到 `photoId`；下载失败也要留 `{photoId: null, error}`。
   - 引用：收到即 `get_msg` 取回原文 + 图，不等回复时再取。
   - 连发：同人同地 90 秒内合并成一个事件，`parts` 保留分段。
2. **线程绑定**：
   - 有 `quote` → `threadId = quote.messageId` 的线程；
   - 无引用但含指代词（这个/那个/上面/刚才）→ 不猜单条，挂「候选」：最近 3 条带图事件；
   - 其余 → 新线程（或按时间并入同一话题）。
3. **判定放在最后**：`isEngaged` / 白名单 / 续话窗口只看成形后的事件。
4. **决策先落盘**：先写 `{eventId, decision: silent|reply|act, at}`，再执行；发送结果另记 `sent|failed`。
   - 好处：崩在发送前，也能看出「她本来打算回」。

### 3.3 禁止

- 不允许「文本为空就判不相关」——空文本可能是图/引用，成形后才有内容。
- 不允许把「最近一张图」的槽位当成唯一真相；图必须带 id 与发送者。

---

## 4. L1：工作记忆的选择与预算

### 4.1 选择顺序（按优先级，预算内取）

```
P1 当前事件（完整，≤500 字/条）
P2 线程祖先：沿 replyTo 回溯到根，整对保留（她的回复 + 被回的那条必须成对）
P3 最近 20 分钟的时间线（倒序取，直到 60% 预算）
P4 相关旧消息：与当前文本关键词/向量相似的最近 3 条（带时间标记）
P5 上一条 episode 摘要（固定 1 条，≤200 字）
```

### 4.2 预算

| 段 | 群聊 | 私聊 |
|---|---|---|
| 原文时间线 | 1800 字 | 1500 字 |
| 压缩摘要 | 400 字 | 400 字 |
| 记忆/episode | 600 字 | 600 字 |
| 身体/自我/关系 | 1200 字 | 1200 字 |

超出时从 P4 开始丢，再压 P3，**永远不丢 P1/P2**。

### 4.3 渲染

```
[16:40] ★ZERO#2869: （发了一张图）[图:img-abc]
[16:41] 主人: 这个分析一下（回 16:40 ★ZERO：分析下这张图）
[16:41] [我] 米汐: 主人，"这个"是哪张？
〔压缩 15:40–16:10〕主人和 ZERO 在争论截图里的数字，没定论。
```

### 4.4 图片策略

- 当前事件 + 它引用的那条：附 `image_url`（真的给模型看）。
- 其余：只给 `[图:id]` + 发送者 + 时间；需要时她自己 `find_photo`。
- 上限：一轮最多 2 张图，避免把上下文塞爆。

### 4.5 观测

每次模型调用记一行 `prompt-stats.jsonl`：

```json
{"at":"…","place":"…","rawChars":812,"summaryChars":0,"memoryChars":210,
 "dropped":2,"images":1,"budget":1800}
```

没有这个，丢上下文只能靠猜。

---

## 5. L1.5：压缩

触发：选出的原文 > 预算。

1. 取最老的 40% 原文；
2. 一次模型调用（温度 0，无工具，输出 ≤200 字）压成「时间范围 + 在场人 + 聊了什么 + 定了什么」；
3. 成功 → 插到原文段顶部，标 `〔压缩 15:40–16:10〕`；
4. 失败 → 丢弃最老 20%，记 `dropped`（并在 A5 里可见）；
5. 限流：每个 place 每小时最多 1 次压缩调用。

---

## 6. L2：段落结算（episode）

### 6.1 触发

- 同一 place 静默 ≥ 20 分钟（主触发）；
- 或话题明显切换（与最近 3 条相似度低）；
- 或跨天（23:00 tick 兜底）。

### 6.2 产出

```json
{
  "id": "ep-20261102-1640-group",
  "place": "group:1000000",
  "from": "16:40", "to": "17:02",
  "participants": ["主人", "★ZERO", "★大風起", "米汐"],
  "topics": ["截图里的数字对不对", "米饭账"],
  "decisions": ["她说要核原始数字，不再复述结论"],
  "open_loops": ["主人还没贴原图"],
  "her_said": ["主人，这个是哪张？"],
  "tone": "被追问、略窘",
  "anchors": [{ "at": "16:41", "quote": "本小姐根本没拿到画面" }]
}
```

约束：

- `topics/decisions/open_loops` 各 ≤3 条，每条 ≤40 字；
- `anchors` 必须逐字摘录（防摘要编造）；
- 解析失败重试 1 次，仍失败则存原文范围标记，不做假摘要。

### 6.3 使用

- prompt 注入最近 3 个 episode（今天）+ 检索命中的 2 个（更早）；
- 「昨天聊了什么」= 查 episodes.jsonl，不查原文；
- 后续同步进记忆库：一条 episode 一个事件 + evidence（可批量，失败重试）。

### 6.4 成本

- 活跃时约每 20–30 分钟 1 次调用，单次输入 ≤4000 字；
- 每天上限 20 次/place，超了只记时间范围不结算。

---

## 7. L3：长期记忆与检索

### 7.1 写

- episode → 记忆库 `being` 事件（tags: place/speaker/audience），`visibility: user`；
- 高显著事实（承诺、决定、偏好）单独写 `curated`；
- 去重：`hash(place + topics + day)`，重复则合并；不直接改 `data/memory/**`，走 MCP。

### 7.2 读

- **依赖方问题**：当前 vector/FTS 是 post-filter（`index-search.mjs:51/64`），已发联调房间；
- 在他们修之前，她自己的召回走**本地** `episodes.jsonl` + `timeline.jsonl` 关键词检索（零依赖），不把正确性押在外部；
- 外部记忆库修好后作为增强，不作为唯一来源。

### 7.3 遗忘

- episode 记录 `touch`（被检索/被提到）→ 注入优先级提高；
- 30 天未触达 → 移入 `episodes-archive/YYYY-MM.jsonl`，不删除；
- 原文时间线按月归档，只保留最近 2000 条热数据。

---

## 8. 失败模式与回退

| 故障 | 行为 |
|---|---|
| 压缩模型调用失败 | 丢最老 20%，记 `dropped`，本轮继续 |
| 结算 JSON 解析失败 | 重试 1 次；仍失败存范围标记，不写假摘要 |
| 发送前崩溃 | 决策已落盘，重启后可见「打算回但没发」 |
| timeline 无限增长 | 每月归档 + 最近 2000 条热数据 |
| 记忆库 401/403 | 本地检索兜底，错误进日志，不影响回复 |

---

## 9. 验收与回放

### 9.1 离线回放（先做，便宜）

用今天的 `timeline.jsonl`（57 条）当 fixture：

1. 依次把每条当「当前事件」，跑 L1 选择函数；
2. 断言：P1/P2 必在；预算不超；被丢的条数有记录；
3. 复现今天那个失败案例：三张图之后「这个」→ 选择结果必须包含正确 `img-*`。

### 9.2 线上检查

- A1–A6 各跑一次，记录原始输出；
- `prompt-stats.jsonl` 连续 1 天无 `dropped>0` 且预算正常，才算 L1 稳定。

---

## 10. 实施顺序与回滚

| 阶段 | 内容 | 风险 | 回滚 |
|---|---|---|---|
| P0 | L0 顺序：补全→线程→判定；决策先落盘 | 低 | 配置 `pipeline: "legacy"` 走旧分支 |
| P1 | L1 选择 + 预算 + 成对保留 + prompt-stats | 中 | 开关 `memoryPipeline: v1` |
| P2 | L1.5 压缩 + L2 结算 + prompt 注入 | 中 | episode 只写不用（`episodesEnabled:false`） |
| P3 | L3 记忆库同步 + 检索 pre-filter 跟进 | 高 | 本地检索始终可用 |

每一步单独提交、单独验收；P1 之前不改判定逻辑。

---

## 11. 不做的事

- 不把全量历史塞进 prompt（注意力稀释、成本随天数线性涨）；
- 不为了「看起来记得」编摘要——宁可标「压缩/丢失」，不许编；
- 不在记忆库侧擅自改检索实现（等联调确认 `authRoots` 格式）。
